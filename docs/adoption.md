# 扩展性前后哨 Skills 落地行动计划

> 背景痛点:AI 偏重当前需求实现 → 代码定制化强、拓展性不足 → 需求一旦变化即大范围返工 → 研发效率下降、代码质量失控。
> 目标:用两个月把"不好扩展"问题从**事后返工**转变为**事前设计 + 事中门禁 + 事后量化验证**。

## 一、痛点与机制对应(为什么是这套 skill)

| 痛点 | 根因 | 对应机制 | 实测证据 |
|------|------|---------|---------|
| AI 偏重当前需求实现 | 编码前无人强制枚举"未来会变什么" | 前哨 Phase A:8 维度 × 24 信号变化点扫描,逐条登记,不凭感觉跳过 | RED-1 基线:无 skill 时 AI 设计零变化点讨论;GREEN-1:同场景产出 9 条变化点 |
| 代码定制化强、拓展性不足 | 扩展机制靠 AI 即兴发挥,无成本约束 | Phase B:T1/T2/T3 裁决矩阵 + 11 预设模式目录(抽象成本最低优先)+ T3 仅记录防过度设计 | 演示中支付渠道自动落策略模式、通知落观察者,均有 ADR 与迁移触发条件 |
| 需求变化 → 大范围返工 | 波及面在编码时不可见,变更时才发现 | Phase C 门禁落仓(依赖规则测试)+ 后哨变更模拟(真实实施预判变更、度量四指标波及面) | 演示实测:新增一个支付渠道需改 2 个既有文件 → 判超标 H,提前暴露 |
| 质量难以控制 | "测试过了"≠"可扩展",AI 评审主观 | 完成门 5 条 + H 级双代理对抗复核 + 变异抽查防假测试 | 变异抽查实测抓到通知逻辑零测试覆盖缺口 |

**核心杠杆:门禁落仓。** 依赖规则测试提交进仓库后,任何 AI 会话(哪怕未装 skill)编码时都会被约束——这是不依赖任何人自觉的机制。

## 二、落地原则

1. **分级使用,防流程疲劳**——全流程只用于核心域,小改动零成本只受门禁约束
2. **门禁先行**——第一阶段就把依赖规则测试铺进 CI,价值最大、阻力最小
3. **登记表是活文档**——每次迭代回顾校准命中率,预测错了就改裁决
4. **度量驱动**——北极星指标是"需求变更返工面",所有阶段围绕它验证收益

## 三、四阶段落地路线(8 周)

### Phase 0:准备(第 1 周)

| 行动 | 具体操作 | 产出 |
|------|---------|------|
| 安装 skill | `git clone https://github.com/jingwang-0415/extensibility-skills`,两个目录复制到团队 AI 助手 skills 目录(OpenCode: `~/.config/opencode/skills/`;Claude Code: `~/.claude/skills/`) | 团队全员可用 |
| 选 1-2 个试点模块 | 选择标准:①业务核心 ②近 6 个月确实变过 3+ 次的模块 ③有明确演进方向(如即将多渠道/多租户) | 试点清单(1 页) |
| 摸基线 | 对试点模块近半年 git 历史做一次统计:每次需求变更平均**修改既有文件数 / 修改行数 / 涉及测试破坏数**(这就是当前返工面) | 基线数字,Phase 3 对比用 |
| 团队速训(60 分钟) | 讲三件事:T1/T2/T3 怎么裁决、过表确认时用户看什么(可能性×影响面)、门禁红了怎么办(先看是不是设计裁决错了,而不是删测试) | 团队对齐 |

**退出标准:** 基线数字出来了;试点模块确定;至少 2 人会跑前哨。

### Phase 1:试点(第 2-4 周,1-2 个核心模块,全流程)

每个进入开发的需求执行第四节的 SOP(全量版)。同时:

| 行动 | 具体操作 |
|------|---------|
| 每需求跑前哨 | AI 会话约 15-30 分钟;**人工过表 10-15 分钟**(增删变化点、确认裁决)——这步不能省,是预测质量的来源 |
| 门禁进 CI | 依赖规则测试(import-linter/ArchUnit/dependency-cruiser 按栈)并入流水线,违规=挂 |
| 合并前跑后哨 | 含变更模拟(worktree 实施抽样的 T2 变更)+ 变异抽查;H 级发现全修复才算完 |
| 周会看三个数 | 依赖规则违规数、变更模拟达标率、登记表新增/修订条数 |

**退出标准(4 周末评估):** 试点模块 `.extensibility/` 登记表覆盖全部 T2 扩展点;门禁全绿;≥1 次变更模拟在真实需求变更前命中(即:后预测的变后来真的来了,或提前暴露了波及面)。**若 4 周内登记表命中率极低(<20%)且团队反馈过重 → 收缩到只保留门禁+后哨,前哨仅核心域月度跑。**

### Phase 2:推广(第 5-6 周,分级铺开)

按第五节分级策略,把全流程铺到核心域,轻量版铺到常规需求。存量模块用后哨降级模式(自底向上归纳变化点,`[推断]` 标注,确认后重建登记表)——**只处理高变更频率的存量,不搞全量补课**。

**退出标准:** 核心域新需求 100% 走前哨;常规需求 100% 走轻量版;CI 门禁覆盖核心仓。

### Phase 3:制度化(第 7-8 周起,常态运转)

| 行动 | 具体操作 |
|------|---------|
| 迭代回顾校准登记表 | 每迭代 30 分钟:回顾哪些预判变化点发生了(命中)、哪些没预判到的变化发生了(漏判→补录并提升 Layer 2)、哪些 T3 实际来了(升级 T2 并补设计) |
| 复测北极星 | 对比 Phase 0 基线:需求变更返工面(修改既有文件数)是否下降;目标:命中的变化点返工面 ≤ ADR 迁移触发条件声明范围 |
| 沉淀团队模式 | `[自定义机制]` 被 ≥2 项目复用 → 进项目模式清单;领域通用 → 提回 skill 的 Layer 0(给上游仓库提 PR 或 fork 维护) |
| 新人上手 | 新人第一天读 `.extensibility/change-register.md` 即可理解模块的演进假设——登记表成为活文档 |

## 四、单需求标准作业流程(SOP)

| 时机 | 动作 | 执行者 | 产出 |
|------|------|--------|------|
| 需求评审后 | 对 AI 说:"使用 extensibility-design,基于这份需求做变化点分析"——AI 按分类库扫描产出候选登记表 | AI | `.extensibility/change-register.md`(草稿) |
| 评审会/异步 | **过表确认**:逐条增删,调整可能性×影响面;拿不准的标 `[推断]` 下迭代验证 | 需求方+开发 | 已确认登记表 |
| 技术方案 | AI 按裁决矩阵出 T1/T2/T3;T2 从预设模式目录选机制(成本最低优先);产出 ADR + 编码约束 + 依赖规则测试 | AI+开发评审 | design-decisions / design-constraints / RULE 测试入仓 |
| 编码 | 约束段贴进任务描述;门禁已挂 CI,违规即红 | AI 编码 | 代码 + 绿门禁 |
| 合并前 | "使用 extensibility-audit 检视本次实现"——双轨检视 + 变更模拟 + 变异抽查;H 级修复 + 登记表演进请示 | AI+评审人 | audit-reports/audit-NN.md |
| 迭代回顾 | 登记表命中/漏判校准(见 Phase 3) | 团队 | 登记表更新 |

## 五、分级使用策略(防流程疲劳的关键)

| 需求级别 | 前哨 | 后哨 | 增量成本 |
|---------|------|------|---------|
| 核心域大需求(新模块/架构级) | 全流程(过表+ADR+门禁生成) | 全流程(含变更模拟+对抗复核) | 约 1-2 人时/需求 |
| 常规需求(核心域内迭代) | 增量登记(只分析新增变化点,复用既有登记表) | 检视+抽样模拟 1 个点 | 约 0.5 人时 |
| 小改动/bugfix | 不跑 | 不跑,**门禁自动生效** | ≈0(已摊销) |
| 存量高变模块 | 后哨降级模式重建登记表(一次性) | 之后按常规 | 一次性 1-2 人时/模块 |

## 六、度量体系(证明它有用/没用)

| 指标 | 定义 | 采集方式 | 目标 |
|------|------|---------|------|
| **变更返工面(北极星)** | 命中变化点的真实变更所修改的既有文件数 | git log + 登记表关联 | 持续下降,且 ≤ ADR 声明范围 |
| 登记表命中率 | 预判变化点中实际发生的比例 | 迭代回顾人工标注 | 40%+ 即有价值(Change Cases 经验值) |
| 漏判率 | 实际变化中未预判的比例 | 同上 | 持续下降,漏判即补录 |
| 门禁违规率 | CI 依赖规则违规次数/周 | 流水线 | 趋零后回升=架构被侵蚀预警 |
| 变更模拟达标率 | 抽样 T2 模拟"只新增不修改"达标比例 | audit-reports 汇总 | ≥80% |
| 变异抽查存活率 | 变异未被测试抓到的比例 | audit-reports | <20% |

所有数据都在 `.extensibility/` 与 audit-reports 里,可脚本汇总,无需另建平台。

## 七、阻力与对策

| 阻力 | 对策 |
|------|------|
| "流程太重,影响交付速度" | 亮分级表:小改动成本≈0;全流程只在架构级需求;对比一次大返工的成本(基线数字说话) |
| "AI 预测的变化点不准" | 命中率 40% 已值得(未命中的 T3 只是登记表一行字,零成本);过表确认+迭代校准会持续提升 |
| "登记表没人维护,变成死文档" | 后哨每次强制回查登记表(不一致=发现),迭代回顾制度化;死登记表会让门禁立刻报警 |
| "老项目铺不开" | 只做高变更频率存量模块的降级模式重建,不搞全量 |
| "门禁红了就有人想删测试" | 规则语义变更须走登记表演进(请示用户),AGENTS.md 里写明——删测试绕过 = 流程违规 |
| "AI 助手不止一种,各自为政" | skill 遵循 agentskills.io 开放标准,40+ 客户端统一安装;门禁在仓内与工具无关 |

## 八、快速开始(今天就能做的三件事)

1. **装**:`git clone https://github.com/jingwang-0415/extensibility-skills` → 复制两个 skill 目录到你的 AI 助手 skills 目录
2. **试**:挑一个你正在做的需求,对 AI 说"使用 extensibility-design 做变化点分析",过表 15 分钟,感受预测质量
3. **锁**:让前哨把依赖规则测试落进仓库 CI——从这一刻起,即使团队永远不再运行 skill,任何 AI 写代码都会被架构约束管住
