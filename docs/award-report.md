## 一、成果背景:AI 编码规模化带来的新型质量风险

随着 AI 编程助手在研发流程中普及,团队交付速度显著提升,但一个新型质量风险同步显现并持续放大:

**AI 生成代码偏重当前需求的直接实现,忽视未来演进能力。** 具体表现为:接口按当期调用方定制、类型分支硬编码、外部依赖直连、缺少隔离层。代码"能用但不好改"——需求一旦变化,即引发大范围返工,最终导致研发效率下降、架构质量失控、技术债务加速累积。

该问题具备三个特征,使传统手段难以应对:

1. **隐蔽性**:功能测试全绿,问题在架构层,评审阶段才可能暴露,修复成本已放大数十倍
2. **依赖个人经验**:识别"未来不好扩展"传统上依赖资深架构师,不可规模化,且 AI 编码量远超人工评审承载力
3. **业界普遍性**:Thoughtworks 技术雷达(2026年4月)将 "Architecture Drift Reduction with LLMs" 列入评估项,确认 AI 编码加速架构漂移是全球性工程问题,业界尚无标准化解法

本成果的破题思路:**把过去依赖资深开发者经验才能发现的"未来不好扩展"问题,前移到代码生成之前,用可执行机制而非人的自觉来解决。**

## 二、成果概述

本成果是一套遵循 Agent Skills 开放标准的 AI 编程助手扩展性治理技能体系(**"扩展性前后哨"**),以两个智能技能夹住 AI 编码全流程:

```
需求方案 →【前哨】变化点分析 → 扩展性设计(YAGNI 裁决)→ 可执行门禁落仓
        → AI 编码(依赖规则测试在仓,编码期即被约束)
        →【后哨】扩展性检视(双轨)→ 黑盒验证(变更模拟波及面度量)→ 报告修复
```

**核心度量创新:扩展性 = 实施一个预判变更的波及面**(新增文件数 / 是否修改既有文件 / 既有测试破坏数),将不可度量的"架构好坏"转化为可验证的客观指标。

成果形态:2 个智能技能(13 个文件,中文主体)、开源仓库(GitHub,MIT 协议)、完整设计规范与验证证据链、双发行包(独立版/捆绑版)。

## 三、主要创新点

### 创新点 1:扩展性治理范式从"事后评审"前移为"事前裁决 + 事中门禁 + 事后量化验证"全链路

业界现状:扩展性靠编码后的人工架构评审(滞后、主观、依赖个人)或事后重构(成本最高)。

本成果在 AI 编码**之前**强制执行变化点结构化枚举(8 维度 × 24 信号分类库,源自 Scott Ambler Change Cases 方法并结构化扩展),对每条变化点做出显式三级裁决——T1 立即实现 / T2 预留扩展点 / T3 仅记录——既治理"欠设计"也治理 AI 另一个典型病症"过度设计"(投机性抽象)。

### 创新点 2:架构约束 TDD 化——可执行门禁落仓,独立于技能与工具存活

本成果在设计期即生成栈适配的依赖规则测试(Java→ArchUnit、Python→import-linter、JS/TS→dependency-cruiser)并提交进代码仓库、挂入 CI。**从落仓一刻起,任何 AI 会话(即使未安装本技能)编码时都会被架构约束管住。**

这是本成果中最具工程价值的机制:治理效果不依赖任何人运行技能、不依赖特定 AI 工具,将"架构守卫"变成与代码同生命周期的资产。对应 Thoughtworks 雷达 Adopt 级实践 "Curated Shared Instructions" 与 Trial 级 "Feedback Sensors for Coding Agents" 的组合落地。

### 创新点 3:变更模拟波及面度量——将架构评估从纸面推演变为可执行验证

业界最接近的方法是 CMU SEI 的 ATAM/SAAM 场景化架构评估,但停留在专家纸面推演。本成果将"预判的未来变化"在独立 worktree 中**真实实施一遍**,度量四项波及指标(新增文件数 / 修改既有文件数 / 修改行数 / 既有测试破坏数),以"只新增、不修改"为达标线,验证后默认回滚。

演示项目实测:对预留扩展点的支付模块模拟"新增一个支付渠道",实测需修改 2 个既有文件,系统自动判为超标 H 级发现——**返工风险在需求期即被量化暴露,而非数月后真实变更时引爆。**

### 创新点 4:对抗式质量门禁,抑制 AI 验证环节的自证偏差

AI 自查 AI 的输出存在"自证偏差"与"永远绿"假测试风险。本成果引入三重对抗机制:H 级发现双代理对抗复核(独立会话、相同证据、盲验,分歧交人工裁决);变异抽查(对核心逻辑注入变异,测试必须变红);五条完成门(登记表 100% 回查 / 依赖规则全绿 / 验收测试全绿 / 抽样变更模拟达标 / H 级发现全修复)。演示中变异抽查实际抓到一个测试零覆盖缺口,验证了机制有效性。

### 创新点 5:技能自身的有效性经 TDD 实证——AI 治理工具的可信度方法论

业界 AI 技能/提示词工程普遍缺乏有效性验证。本成果将测试驱动开发方法应用于技能本身:先跑无技能基线(RED:实测证明 AI 设计零变化点讨论、硬编码单渠道),再装技能复跑(GREEN:同场景产出 9 条变化点、策略模式选型、落仓门禁),逐字记录、字节级可复核。**为"AI 流程工具是否真的有效"提供了可复现的验证范式。**

## 四、技术方案要点

| 模块 | 机制 |
|------|------|
| 变化点分类库 | 三层模型:Layer 0 通用分类库(8 维度 24 信号)→ Layer 1 项目登记表(活文档)→ Layer 2 自扩展回流 |
| YAGNI 裁决 | 可能性 × 影响面矩阵,自上而下首行命中;T2 成本上限"每扩展点 ≤ 一层抽象 + 文档" |
| 预设模式目录 | 11 个经典扩展模式映射到 24 信号(策略/防腐层/插件注册表/观察者/管道等),抽象成本最低优先,含逃生舱与反例 |
| 双轨检视 | 确定性(依赖规则测试)+ LLM 语义(登记表回查、模式符合性、6 类 Change Preventers 坏味道) |
| 跨平台可移植 | 遵循 agentskills.io 开放标准(40+ 客户端兼容),零环境强依赖,五级能力降级(无子代理/git/测试框架/依赖工具/登记表均有降级路径且显式标注) |

## 五、实施过程

历经调研→设计→开发→验证四阶段,全程采用双代理门禁开发(每任务独立实施者 + 独立评审者):

1. **业界调研**(Change Cases / 进化架构 Fitness Functions / ADR / ATAM / Thoughtworks 雷达):确立"站在优秀实践上做两处拓展"——设计期生成门禁、变更模拟可执行化
2. **规范设计**:完成设计规范书(业界实践对照表、依赖分层策略、双发行包方案)
3. **开发实施**:15 个任务全部通过"实施者+评审者"双代理门禁,评审者实测纠出并修复 8 处真实缺陷(grep 模板静默失效、门禁指标漏计删除/重命名、表格渲染缺陷、裁决矩阵歧义等)
4. **端到端验证**:示例项目植入 4 类典型缺陷,前哨/后哨全流程闭环验证
