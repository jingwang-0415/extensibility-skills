# 代码扩展性检视

默认用中文输出，保留必要的英文技术术语。判断目标是：在有依据的业务变化下，代码能否以可控的修改范围和回归风险完成扩展。不要用设计模式数量、接口数量或“完全不修改旧代码”衡量扩展性。

这是可独立使用的专项 skill。若与通用代码检视共同使用，合并重复问题，并补充扩展场景和修改面证据。默认只读评审；仅在用户要求修改时实施修复，不因检视而自动生成仓库知识文档或开展全仓重构。

## 确定范围与业务变化依据

- 优先使用用户提供的 MR/PR、commit、diff 或文件范围。对差异评审区分本次引入、加剧的问题与历史问题；无关历史问题不要作为本次变更缺陷。用户要求全模块评估时，才覆盖其已有设计问题。
- 未指定范围时，先查看当前仓库及变更，选择最小相关模块并说明范围；多个不相关目标无法判断时再询问。没有可用代码时，请用户提供路径或变更目标，不输出虚构发现。
- 阅读适用的仓库规则、相关需求、架构文档、已有实现和测试。文档与实现冲突时，列出差异，不能默认文档一定正确。
- 为每个选定场景记录：变化内容、依据、必须保持不变的行为。依据优先级为明确需求、已有多种实现或历史变更证据、最后才是假设。
- 优先深入最有代表性的场景，例如新增支付渠道、计费规则、消息类型或供应商。只有一个实现且没有扩展需求时，不强行要求插件框架或策略接口。
- 没有明确未来需求仍可检查现有重复和耦合，但对假设性扩展只能作条件分析；不要将假设写成已确定的业务计划或缺陷。

## 推演一次扩展

对每个有依据的场景，沿实际执行路径推演新增能力需要做什么。先查入口、分派、业务处理、数据或外部交互和测试，再按需要检查配置、注册、序列化和部署。不要仅凭一个方法或一个 `switch` 下结论。

记录一份简短的修改面表：

| 扩展场景及依据 | 需新增的实现 | 需修改的既有位置 | 必须保持的行为 | 风险与证据 |
| --- | --- | --- | --- | --- |

使用实际文件和符号，不编造修改数量。区分正常接入成本（新增实现、注册、配置、迁移和测试）与可避免的传播成本（同一规则在多处重复维护、修改无关模块、复制流程）。改动多个文件本身不是缺陷。

针对变化点，检查新增实现能否独立验证，以及已有实现能否通过原有调用契约继续工作。接口存在并不证明扩展性成立；需要沿接入路径确认它确实被使用。

## 专项检查维度

按场景选择相关维度，不要求为无关维度凑问题。

### 变化传播与业务分派

- 同一业务类型或能力列表是否散落在分派、校验、转换、计费、持久化和通知等位置；新增类型是否容易漏改并产生不一致？用实际重复位置说明后果。
- 稳定流程是否夹杂具体渠道或供应商的细节，新增策略是否需要复制整个流程或触碰无关分支？先判断提取局部方法、集中映射或隔离适配器是否已经足够。
- 区分有意封闭的状态机、有限枚举和真正开放的变化点。穷尽分支有时能让编译器暴露遗漏，改成动态注册反而可能降低安全性。

### 抽象与依赖边界

- 核心业务是否直接依赖供应商 SDK、存储模型或具体实现，导致替换或增加实现时外部细节传播到多个业务模块？检查已有适配层是否已隔离该风险。
- 不同策略是否被迫实现不适用的方法、传递大量类型专属参数、依赖调用顺序或返回占位值？这些差异是否说明能力边界划分不当？
- 是否通过继承复用流程却依赖可变内部状态、未说明的覆写顺序或具体子类判断，使新增子类破坏原有假设？优先明确契约，再评估组合是否更合适。
- 是否已有多层转发、万能上下文、字符串参数集合或泛化框架，却没有实际变化点支撑？过度抽象同样是扩展成本。

### 扩展点接入与行为契约

- 从新增实现追踪到最终调用：是否仍有固定白名单、硬编码工厂或二次类型判断，导致实现已注册但无法使用？
- 对注册表、SPI、依赖注入或插件机制，按需检查标识唯一性、重复处理、缺失策略、顺序、优先级、默认行为和错误反馈。不要未经检查就假定框架如何选择实现。
- 检查各实现对输入输出、异常、事务、幂等、重试、线程安全和资源生命周期的约定，是否允许新增实现保持业务不变量。仅审查与扩展点相关的部分。
- 对 Java/Spring，可追踪接口、工厂、`ServiceLoader`、Bean 条件、集合注入及代理调用；以实际框架版本和项目约定为准。对其他语言使用其等价机制，不强套 Java 模式。

### 数据与对外契约演进

- 新增类型或字段是否会影响旧消费者、历史数据、序列化、数据库约束、缓存键、配置及混合版本部署？区分内部类型与跨进程契约。
- 未知值应该拒绝、忽略、保留还是使用默认行为，需由业务契约决定。不得为了“兼容”把未知类型静默分派到错误策略。
- 若扩展依赖迁移或发布顺序，指出必要条件以及现有方案是否满足；不要把正常的 schema 迁移本身判为扩展性差。

### 独立验证与回归隔离

- 新增实现是否可以通过统一行为契约及自身差异测试验证？测试是否覆盖选择正确实现、未注册或冲突情况，以及原有实现保持不变？按实际风险选择场景。
- 新增实现是否要求修改大量与其无关的测试或全局共享状态？查明这是有意的契约变化，还是实现细节泄漏造成的耦合。
- 使用已有编译、定向测试或契约测试验证关键结论；纯评审不为形式上的覆盖率新建测试体系。不运行无法解释用途的重型检查。

## 证据与改进门槛

正式问题需建立完整因果链：**有依据的扩展场景 → 具体代码约束 → 不必要的修改或无法接入 → 可说明的后果**。

- 证据包括文件与行号、调用链、重复规则、实际接入路径、既有测试或需求。仅凭类名、方法长度、分支数、缺少设计模式不足以形成发现。
- 检查反证：已有适配层、代码生成、集中注册、编译期穷尽检查或契约测试是否已经解决疑点。没有证据支持时撤回判断或降为“需要确认”。
- 优先建议最小有效改进，如集中一处规则、隔离供应商转换、明确扩展契约、拆分不相关能力。不要直接把所有分支改成策略模式。
- 提出接口、注册表或插件机制时，说明它隔离哪个已知变化点、减少哪些既有修改，同时交代新增抽象和运行时校验成本。
- 若更小改动已足够，选择更小改动；若收益没有业务证据，保留现有设计并注明启用重构的条件。

判定示例：新增渠道必须同步修改三处独立渠道清单，且已有需求要求接入第三方渠道，可以报告漏接入风险；一个封闭状态枚举在一处做穷尽分支，不能仅因存在 `switch` 就要求策略模式；接口新增抽象方法导致已有实现不能编译，需要先确认是否为有意的契约升级及调用范围。

## 输出

先给结论和有证据的问题，再给必要的修改面分析。按任务规模裁剪输出，不输出空白模板或无关检查清单。用户指定格式时服从其格式。

每条发现包括：

- **[级别] 标题**及精确代码位置；涉及重复规则时列出关键相关位置。
- **扩展场景与依据**：何种变化会触发问题，哪些已有行为应保持不变。
- **证据与影响**：实际调用或接入路径、需连带修改的位置、遗漏或耦合的具体后果。
- **最小建议**：如何缩小变化传播或补足契约，以及必要的代价。
- **验证方法**：用什么行为或测试证明新场景可接入且原有行为保持。

按实际影响分级，不按使用哪种模式分级：

- **P1**：已要求或已接入的扩展会导致高置信度的严重运行错误、数据风险或对外契约破坏。
- **P2**：已有需求或现有多实现证据表明，存在显著且可避免的修改传播、扩展点失效、规则分散或兼容风险。
- **P3**：影响较小且有证据的局部维护成本问题。
- **改进建议 / 需要确认**：可选设计优化、假设性未来需求或缺少运行与业务信息的疑点，不包装为确定缺陷。遇到实际严重事故风险时，可按仓库规范使用更高级别并解释。

最后简要说明评审范围、代表性扩展场景的修改面、已验证与未验证事项。有疑点但无高置信度发现时明确说“在本次范围和扩展场景下，未发现有充分证据的扩展性问题”，不能宣称代码能够适应所有未来需求。不作没有测量依据的工时估算或扩展性百分制评分。
